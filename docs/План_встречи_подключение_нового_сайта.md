## 1. Цель и рамки обсуждения

### 1.1. Что обсуждаем

Есть действующая программа (pipeline) для генерации текстов по категориям/характеристикам.

Исторически она работала с одной моделью входных данных. Сейчас нужно подключить другие сайты, у которых:

- другие исходные данные;
- другая семантика;
- другие требования к текстам;
- возможно, другие настройки AI и финальной выгрузки.

При этом сайт адаптируется под контракт программы, а не программа переписывается под каждый сайт.

### 1.2. Что не является целью этой встречи

- разбор внутреннего кода;
- финальное ТЗ на доработку системы;
- обещание конкретных сроков интеграции без понимания данных;
- запрос «пришлите JSON» без понимания, что у стороны сайта реально есть.

## 2. Организационная модель: сайт, домены, пользователи, права

### 2.1. Как устроена работа в системе

В системе есть уровни:

1. **Сайт** — отдельная сущность проекта (например, текущий основной сайт и подключаемый новый).
2. **Домен / регион** — внутри сайта (например, default / kz / eu).
3. **Проект** — рабочая единица генерации внутри сайта и домена.
4. **Пользователи и права** — доступ выдаётся на сайт/домен (чтение / запись / удаление).
5. **Профиль** — логин, email, смена пароля, 2FA, управление своими проектами/бэкапами.
6. **Админка** — пользователи и права, API-ключи, просмотр проектов, статистика AI, аудит, бэкапы.

Важно: блоки текстов и часть настроек привязаны к связке **сайт + домен**, а не только к «названию сайта».

## 3. Общая схема pipeline (ориентир для всех блоков)

| Этап | Что делает | Что нужно от нового сайта |
|------|------------|---------------------------|
| Фаза 1 | Категории и характеристики | Обязательно |
| Фаза 2 | Маркеры / семантика / приоритеты | Желательно (можно стартовать без неё) |
| Фаза 3 | Блоки, переменные, AI-инструкции | Обязательно для уникализации текстов |
| Фаза 4 | Сборка промптов | Не готовить со стороны сайта |
| Фаза 5 | AI-генерация | Нужны решения по AI / ключам / ограничениям |
| Фаза 6 | Синонимизация | Общая база; нужны ограничения «не заменять» |
| Фаза 7 | Постобработка и выгрузка | Требования к финальному виду и формату |

Принцип: сторона сайта готовит/согласовывает входные сущности и требования; система формирует промпты и проходит генерацию.

## 4. Фаза 1 — категории и характеристики

### 4.1. Зачем блок

Фаза 1 — фундамент. Без корректных категорий и характеристик дальше pipeline не запускается нормально.

Программе нужен не «любой каталог», а данные, из которых однозначно получаются:

- название категории;
- характеристики;
- значения характеристик по товарам;
- по возможности метрика для приоритизации значений (например, число предложений).

### 4.2. Эталонный вход

Ожидаемая логика эталонного JSON:

- `ПараметрыТовара.Наименование` — категория;
- `ПараметрыТовара.Характеристики[]` — описание характеристик (`ID`, `Наименование`, единица, приоритет и т.п.);
- `Товары[].Характеристики` — значения характеристик по товарам.

Допускается, что исходные данные сайта имеют другую структуру — тогда нужен слой преобразования/маппинга к эталону.

### 4.3. Эталонный результат фазы 1

После обработки должны получиться:

- `category`
- `characteristics[]` с полями вида:
  - `char_id`
  - `char_name`
  - `unit`
  - `is_unique`
  - `values[{value, items_count, offers_sum, percent}]`
